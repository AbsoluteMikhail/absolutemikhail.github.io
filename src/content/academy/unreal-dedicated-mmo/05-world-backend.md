Продолжаем [предыдущее занятие](/academy/unreal-dedicated-mmo/04-server-deployment). План встречи с ментором на **120 минут**, с практикой и временем на вопросы. Подробный разбор шагов и примеры добавлю позже. Долгие сборки, загрузки и подготовку окружения оставляем на время между встречами.

## Результат занятия

Разберём, за что отвечают клиент, игровой сервер, backend и база данных. Отправим первый запрос от сервера игры к учебному сервису.

## Стартовая точка

Headless-сервер работает. До этого блока выбираем стек backend и подготавливаем минимальный сервис с тестовой базой. Его каркас пока не приложен; писать весь веб-фреймворк с нуля на встрече не планируем.

## Собираем и проверяем

### Рисуем путь данных

Клиент сообщает, что хочет сделать игрок, сервер рассчитывает бой, а backend проверяет учётную запись и хранит постоянные данные. Один небольшой backend может выполнять несколько задач; отдельные микросервисы на каждую кнопку не требуются. Определяем, какие данные теряются при падении симуляции.

### Подключаем подготовленный API

Отправляем запрос сервер → backend, задаём время ожидания и разбираем ответ. Клиент не получает доступ к БД или служебный ключ сервера. В C++ не блокируем игровой поток ожиданием HTTP или SQL, обрабатываем ответ с учётом времени жизни объекта.

### Проверяем недоступность сервиса

Проверяем, как игра реагирует на ошибку, задержку и неверный ответ. Вместо бесконечного ожидания игрок должен получить понятный результат. По логам должно быть видно, к какой операции относится запрос; секреты в них не записываем. Здесь пока нет полноценной регистрации, почты и платёжной системы.

## Где легко ошибиться

- Клиент напрямую пишет постоянные данные в БД.
- Игровой поток ждёт сетевой ответ и останавливает симуляцию.

## Проверка результата

- Для каждой части схемы понятно, какие данные она хранит и что с ними делает.
- Сервер игры получает проверенный ответ от учебного backend.
- Недоступный API не блокирует игровой поток и не выдаёт ложный успех.

## Домашнее задание

Добавьте один read-only запрос и проверьте timeout, удаление получателя и неверный ответ. Опишите, что должно оставаться доступным при отказе backend.
