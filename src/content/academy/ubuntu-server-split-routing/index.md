Эта статья выросла из возни с моим VPS. Малена, мой Telegram-бот на Python, перестала нормально связываться с серверами Telegram. Заодно пришлось разбираться с DNS и загрузкой пакетов через APT. На VPS работали и другие службы, а доступ по SSH терять совсем не хотелось.

С Маленой можно [пообщаться в Telegram](https://telegram.me/MalenaOnline_bot). Кстати, на обложке тоже она =) А если захочешь сделать своего Telegram-бота, скоро в Академии появится мини-курс по их вайбкодингу.

В моём случае помогло выборочное использование VPN: запросы бота и APT пошли через него, а SSH и остальные службы сохранили обычный маршрут. Я настроил на VPS локальный прокси Xray, который принимал запросы нужных приложений и передавал их удалённому узлу из VPN-профиля.

Я описываю свой опыт раздельной маршрутизации трафика приложений на сервере. Материал не предназначен для рекламы средств обхода блокировок в Российской Федерации или призывов использовать их для этой цели.

## Перед началом

У меня стояла Ubuntu Server 24.04. Чтобы проверять команды на своём сервере, нужно уметь подключаться по SSH, редактировать файлы и выполнять команды с `sudo`. Команды для сервера написаны для Bash, а пример переноса файла с Windows — для PowerShell.

Перед изменениями открой вторую SSH-сессию и проверь доступ к консоли VPS через панель хостера. Она пригодится, если обычное подключение пропадёт.

Для подключения нужен рабочий профиль своего или разрешённого для использования удалённого сервера. Если у тебя купленная подписка, ключ или ссылка для импорта, сначала посмотри [как получить конфигурацию из подписки](#как-получить-и-проверить-json-подписки). Сам удалённый сервер здесь не разворачиваем — подключаемся к готовому.

Для первых запросов используем `example.com`. Когда схема заработает, проверим нужный тебе сервис: у разных адресов доступность может отличаться.

Разбор разделён на восемь шагов: от диагностики до перезагрузки. Дополнительные проверки собраны в [справочнике в конце](#справочник), а ссылки на них стоят рядом с соответствующими шагами. Проходить весь справочник подряд не нужно.

Позже связь снова пропала, и я добавил автоматический выбор рабочего узла из подписки. Это продолжение вынесено в [девятый шаг](#9-обновляем-узел-из-подписки-при-сбое): он пригодится, если первоначальная настройка уже работает, но удалённый сервер иногда становится недоступен.

## Как разделяется трафик

Путь запроса состоит из двух участков. Сначала приложение обращается к Xray на том же VPS. Затем Xray передаёт запрос через подключение из VPN-профиля. То есть локальный прокси принимает запрос, а VPN-подключение определяет, куда он пойдёт дальше.

Это **выборочная маршрутизация через VPN на уровне приложений**. По смыслу — раздельное туннелирование: мы выбираем, какой трафик отправлять через удалённый узел. Для этого указываем адрес прокси только нужным приложениям. Общий VPN-интерфейс не создаём, маршрут Linux не меняем — используем входы Xray и настройки своего профиля.

| Кто отправляет запрос | Куда подключается | Дальнейший путь |
|---|---|---|
| Приложение с SOCKS5 | `127.0.0.1:10808` | Xray → узел из VPN-профиля → сервис |
| APT или HTTP-клиент | `127.0.0.1:10809` | Xray → тот же узел из VPN-профиля → сервис |
| SSH и приложения без прокси | Обычный сетевой интерфейс | Прежний маршрут VPS |

`127.0.0.1` означает «этот же сервер». Числа `10808` и `10809` — порты, на которых Xray принимает подключения. SOCKS5 и HTTP — два способа общения с прокси: приложению подойдёт тот, который поддерживает его библиотека, а для APT используем HTTP.

Пример рассчитан на приложения, запущенные прямо на VPS и умеющие работать с прокси. Для приложений в контейнерах есть [отдельная оговорка](#где-эта-схема-работает).

## 1. Находим место сбоя

### Проверяем ресурсы сервера

Перед изменением сети смотрим, не закончились ли ресурсы:

```bash
uptime
free -h
df -h
df -i
ps aux --sort=-%cpu | head -15
ps aux --sort=-%mem | head -15
```

Смотрим, хватает ли памяти и места, не забрал ли один процесс все ресурсы. У `df -i` отдельная задача: проверить запас inode — записей, необходимых для создания файлов. Они могут закончиться, даже когда свободное место ещё есть. Нагрузку из `uptime` оценивай с учётом числа процессоров: она может расти и из-за ожидания диска.

Если проблема видна здесь, сначала разбираемся с ней. Если ресурсов хватает, переходим к соединению.

### Смотрим, на чём останавливается запрос

Теперь посмотрим, что происходит с обычным HTTPS-запросом. Сначала сервер узнаёт IP по имени через DNS, затем устанавливает TCP-соединение, договаривается о шифровании через TLS и получает HTTP-ответ. Вывод `curl` помогает увидеть, на каком этапе всё остановилось:

```bash
curl -4 -v --noproxy '*' \
  --connect-timeout 5 --max-time 15 \
  https://example.com
```

`-v` показывает ход запроса. `--noproxy '*'` заставляет curl идти напрямую, даже если в окружении задан прокси. Ограничения в 5 и 15 секунд не дадут проверке зависнуть надолго. С `-4` проверяем только IPv4; IPv6 этим запросом не проверяется.

| Что видно в выводе | Что проверять дальше |
|---|---|
| `Could not resolve host` | Разрешение имени |
| `Resolving timed out` | DNS-сервер и локальный резолвер |
| `Connection timed out` | Доступность адреса и порта, маршрут, firewall и удалённый сервер |
| `SSL connection timeout` | Установление TLS, состояние сети и удалённой стороны |
| HTTP `200`, `302`, `401`, `403` | Ответ уже дошёл до HTTP; дальше важен его смысл |
| `SOCKS5 authentication failed` | Реквизиты и метод авторизации прокси |

Сам по себе тайм-аут не объясняет причину сбоя: мы лишь знаем, что не дождались нужного этапа. А `401` или `403` означают, что HTTP-ответ уже получен — возможно, сервис требует авторизацию. `302` сообщает о перенаправлении. Во всех этих случаях работу самого API ещё нужно проверить.

Если ошибка связана с именем хоста или ты не уверен в своём DNS, начни с [проверки и замены адресов DNS](#проверка-и-замена-адресов-dns). Отдельно разобраны [запрос с заданным вручную IP](#запрос-без-обычного-dns-разрешения) и [проверка готового SOCKS5-прокси](#если-уже-есть-внешний-socks5-прокси). Если адрес разрешается, а проблема дальше по соединению, продолжай основной путь.

Для диагностики используй запрос без токена. Прежде чем передать кому-либо вывод `curl`, проверь, нет ли в нём секретов, в том числе в заголовках.

## 2. Готовим профиль и устанавливаем Xray

### Сначала нужен рабочий профиль

Xray нужны адрес удалённого узла, порт, протокол, реквизиты и настройки соединения. Всё это хранится в JSON-конфиге. В зависимости от профиля там могут встретиться VLESS, TLS, REALITY или WebSocket. Здесь берём уже рабочие значения из своего профиля.

Ключ, подписка или ссылка для импорта не обязательно содержат готовый JSON для Xray. Попробуй экспортировать конфиг из клиента или запросить его у администратора сервиса. Если нужно разобраться с форматом, загрузкой JSON или выбором профиля, это описано в [разделе о подписках](#как-получить-и-проверить-json-подписки).

Начинать проще с одного удалённого выхода. Цепочки, FakeDNS и балансировщики добавляют зависимости, которые тоже придётся проверить.

Храни конфиг и ссылку подписки как пароли: в них могут быть ключи, UUID и другие реквизиты. Не отправляй их в публичный репозиторий, чат или онлайн-валидатор.

### Скачиваем и распаковываем Xray

Сначала пробуем скачать Xray с GitHub прямо на VPS. У меня загрузка с сервера не проходила, поэтому пришлось скачать архив на свой компьютер и передать его по SSH через настроенный VS Code. Это запасной путь: если VPS скачивает файл сам, перенос с компьютера не нужен.

В примерах пользователь сервера — `absolute`, а папка Xray — `/home/absolute/xray`. Замени их на свои во всех командах, в том числе в файле службы ниже. Пользователь должен уже существовать. Службу назовём `app-xray`.

Проверяем архитектуру сервера:

```bash
uname -m
```

Для `x86_64` нужен `Xray-linux-64.zip`. Для ARM выбери подходящий архив в [официальных релизах Xray-core](https://github.com/XTLS/Xray-core/releases) и замени имя файла в командах.

Дальше показана установка из архива. Скачаем ли мы его прямо на VPS или перенесём с компьютера, папка и последующие команды будут одинаковыми. Здесь же есть [готовый официальный установщик](#готовый-установщик-xray), но он использует свои пути и службу.

Подготовим папку на VPS под пользователем `absolute`:

```bash
umask 077
mkdir -p /home/absolute/xray
cd /home/absolute/xray
```

### Загрузка прямо на VPS

Попробуем скачать архив релиза с отметкой Latest на GitHub. Для конкретной версии подставь ссылку на её ZIP из официальных релизов. Так мы проверим, доступен ли сам файл: открывающейся главной страницы GitHub для этого недостаточно.

```bash
curl -fL --connect-timeout 10 --max-time 120 \
  https://github.com/XTLS/Xray-core/releases/latest/download/Xray-linux-64.zip \
  -o /home/absolute/xray/Xray-linux-64.zip
```

Если команда завершилась без ошибки и архив скачан, переходи к [проверке и распаковке](#проверка-и-распаковка-архива). Если нет, прочитай сообщение curl. Например, `404` может означать ошибку в ссылке. Если проблема именно в доступе с VPS, попробуй перенос с компьютера, как в моём случае.

### Если архив не скачивается с сервера

Скачай тот же архив на свой компьютер с [официальной страницы релизов](https://github.com/XTLS/Xray-core/releases). Передать его на VPS можно удобным тебе способом:

- **Через приложение.** Я использовал VS Code с подключением по SSH. В своём клиенте с поддержкой загрузки файлов или SFTP открой удалённую папку `/home/absolute/xray` и загрузи туда ZIP. Если доступно перетаскивание, перенеси файл из локального проводника в эту папку. Точные действия зависят от клиента; про подключение по SSH можно прочитать в [документации VS Code](https://code.visualstudio.com/docs/remote/ssh).
- **Через консоль.** На Windows можно открыть PowerShell в папке со скачанным архивом и выполнить:

```powershell
scp .\Xray-linux-64.zip absolute@SERVER_IP:/home/absolute/xray/
```

Замени `SERVER_IP` на адрес VPS и проверь имя пользователя. Команда передаст архив в подготовленную папку по защищённому соединению. После передачи вернись в терминал сервера.

### Проверка и распаковка архива

Сверь SHA-256 архива с контрольной суммой, опубликованной для **того же релиза**. На сервере хеш показывает `sha256sum /home/absolute/xray/Xray-linux-64.zip`, на Windows — `Get-FileHash .\Xray-linux-64.zip -Algorithm SHA256`. Важно именно сравнить значения, а не просто вычислить хеш.

Если обновляешь существующую установку, перед распаковкой сохрани рабочую версию и конфиг.

Независимо от способа загрузки архив теперь лежит в `/home/absolute/xray`. Распаковываем и смотрим версию:

```bash
cd /home/absolute/xray
python3 -m zipfile -e Xray-linux-64.zip .
chmod +x xray
./xray version
```

Python позволяет распаковать ZIP, даже если `unzip` пока не установлен. На этом установка из архива закончена: переходи к [настройке входов](#3-настраиваем-входы-для-приложения-и-apt).

Сохрани вывод `xray version`: при ошибке он поможет проверить совместимость профиля с версией Xray. Версия Ubuntu сама по себе не определяет версии Xray и Python-библиотек.

### Готовый установщик Xray

Если Xray уже распакован по шагам выше, этот подраздел пропусти. Готовый скрипт [Xray-install](https://github.com/XTLS/Xray-install) можно выбрать вместо ручной установки, если загрузка с GitHub работает:

```bash
curl -fL --connect-timeout 10 --max-time 60 \
  https://raw.githubusercontent.com/XTLS/Xray-install/main/install-release.sh \
  -o /tmp/install-xray.sh
less /tmp/install-xray.sh
```

После проверки скрипта:

```bash
sudo bash /tmp/install-xray.sh install
```

Установщик обычно помещает программу в `/usr/local/bin/xray`, конфигурацию — в `/usr/local/etc/xray/` и создаёт службу `xray.service`. Проверь её настройки через `systemctl cat xray`, включая права пользователя на чтение конфига.

Если выбрал этот способ, подставляй его пути в следующие команды и используй уже созданную службу. Второй экземпляр Xray на тех же портах запускать не нужно.

## 3. Настраиваем входы для приложения и APT

В конфиге Xray используются три названия: **inbound** — вход, **outbound** — выход к удалённому узлу, **routing** — правила между ними. Добавим входы для приложений и укажем, в какой выход направлять их запросы.

Сохрани рабочий профиль как `/home/absolute/xray/app-xray.json`. До изменения сделай защищённую копию с новым именем, не перезаписывая прежнюю:

```bash
cd /home/absolute/xray
chmod 600 app-xray.json
cp -p -n app-xray.json app-xray.before-proxy.json
nano app-xray.json
```

Файл откроется в редакторе `nano`. После правок нажми **`Ctrl+O` → `Enter` → `Ctrl+X`**: сохранить, подтвердить имя файла, выйти. `Ctrl+C` для этого не подходит. Так же сохраняются остальные файлы ниже. Краткая памятка — в [документации nano](https://www.nano-editor.org/dist/latest/cheatsheet.html).

Добавим два входа: SOCKS5 на порту `10808` и HTTP на `10809`. Ниже **только фрагмент** для массива `inbounds`; рабочий профиль целиком он не заменяет:

```json
{
  "inbounds": [
    {
      "tag": "socks",
      "listen": "127.0.0.1",
      "port": 10808,
      "protocol": "socks",
      "settings": {
        "auth": "noauth",
        "udp": false
      }
    },
    {
      "tag": "apt-http",
      "listen": "127.0.0.1",
      "port": 10809,
      "protocol": "http",
      "settings": {}
    }
  ]
}
```

Если `inbounds` уже есть, измени его содержимое — второй ключ с тем же именем добавлять не нужно. Теги и порты не должны повторяться. Остальную часть рабочего профиля сохрани: `outbounds`, `streamSettings`, `routing`, DNS и связанные файлы.

Оба входа слушают `127.0.0.1`. Не меняй его на `0.0.0.0`: без аутентификации прокси может стать доступен посторонним. При этом другие процессы на самом сервере смогут к нему обратиться. Если на VPS есть пользователи, которым ты не доверяешь, понадобятся дополнительные ограничения. Подробности настроек — в документации [SOCKS](https://xtls.github.io/en/config/inbounds/socks.html) и [HTTP](https://xtls.github.io/en/config/inbounds/http.html).

### Связываем входы с нужным выходом

Допустим, у рабочего удалённого outbound уже есть `"tag": "proxy"`. Тогда в `routing.rules` можно поставить первым такое правило:

```json
{
  "type": "field",
  "inboundTag": ["socks", "apt-http"],
  "outboundTag": "proxy"
}
```

Правило читается так: «Всё, что пришло через `socks` или `apt-http`, отправить в выход `proxy`». Добавляем его как элемент массива `routing.rules`. Имя `proxy` должно совпадать с тегом рабочего удалённого выхода — переименование прямого выхода `freedom` в `proxy` не превратит его в удалённый.

Xray читает правила сверху вниз и выбирает первое подходящее. Если совпадений нет, используется первый outbound. Поэтому после настройки обязательно проверим реальный запрос. Подробнее — в [документации маршрутизации](https://xtls.github.io/en/config/routing.html).

Это правило подходит, когда весь трафик двух входов нужно отправлять в один выход. Если в профиле есть исключения для DNS или внутренних адресов, балансировщик, FakeDNS либо свой скрипт маршрутизации, сначала проверь их логику и порядок. Иначе новое правило может сработать раньше нужного исключения.

## 4. Проверяем, что запрос проходит через прокси

Сначала попросим Xray проверить конфиг, не запуская службу:

```bash
cd /home/absolute/xray
./xray run -test -config ./app-xray.json
```

Если всё в порядке, команда завершится успешно; обычно появится `Configuration OK.`. Если нет — читаем ошибку и проверяем JSON, теги, версию Xray и связанные файлы. Соединение с удалённым узлом эта команда ещё не проверяет.

Запускаем вручную:

```bash
./xray run -config ./app-xray.json
```

Оставляем Xray работающим в первом терминале. Во втором смотрим, открылись ли нужные порты:

```bash
sudo ss -ltnp '( sport = :10808 or sport = :10809 )'
```

В списке должны появиться `127.0.0.1:10808` и `127.0.0.1:10809`, открытые нашим процессом. Если порт уже занят, сначала выясни, какой программой. Не останавливай неизвестную службу наугад.

Теперь сравним внешний адрес прямого и проксированного запроса:

```bash
curl -4 --noproxy '*' --max-time 10 https://api.ipify.org
curl --noproxy '' --proxy socks5h://127.0.0.1:10808 \
  --max-time 20 https://api.ipify.org
```

Первая команда показывает внешний IP прямого запроса, вторая — запроса через прокси. Разные адреса помогают подтвердить, что пути отличаются. Если адрес совпал, проверь правило и выбранный outbound. Совпадение не обязательно означает ошибку: оба подключения могут выходить в интернет через общий NAT-шлюз.

Если прямой запрос не проходит, адрес из панели VPS даст ориентир. Но адрес входящих подключений иногда отличается от исходящего, поэтому такое сравнение не всегда точно. Сервис проверки IP видит адрес и время запроса; при необходимости используй свой диагностический адрес.

Теперь проверим HTTPS-запрос и выведем только код ответа и время:

```bash
curl --noproxy '' --proxy socks5h://127.0.0.1:10808 \
  --max-time 20 -sS -o /dev/null \
  -w 'HTTP: %{http_code}, Time: %{time_total}s\n' \
  https://example.com
```

После `example.com` подставь адрес своего API без секретов в URL, затем проверь обычное действие приложения. Именно оно покажет, решена ли исходная проблема. Если curl вывел `000`, HTTP-ответ получить не удалось.

## 5. Настраиваем автозапуск

Ручной запуск помог проверить соединение. Теперь поручим systemd запускать Xray вместе с сервером и перезапускать при сбое. Для нашей установки из архива создаём файл службы:

```bash
sudo nano /etc/systemd/system/app-xray.service
```

```ini
[Unit]
Description=Application Xray Proxy
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=absolute
WorkingDirectory=/home/absolute/xray
ExecStart=/home/absolute/xray/xray run -config /home/absolute/xray/app-xray.json
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
UMask=0077

[Install]
WantedBy=multi-user.target
```

После вставки сохрани файл: **`Ctrl+O` → `Enter`**, затем выйди из nano через **`Ctrl+X`**.

У пользователя из `User` должны быть права на чтение конфига и запуск программы. Для прослушивания портов выше 1024 права root не нужны. А `network-online.target` определяет порядок запуска: доступность внешнего API он не гарантирует.

Останавливаем ручной Xray через `Ctrl+C`, затем запускаем службу:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now app-xray
systemctl status app-xray --no-pager
sudo journalctl -u app-xray -n 50 --no-pager
```

Повтори запрос через SOCKS5: статус `active` означает, что служба работает, но не подтверждает соединение с нужным сервисом. Если процесс падает, смотри журнал. Частые причины — неверный путь, недостаточные права, занятый порт или ошибка в конфиге. Перед публикацией журнала проверь его на секреты.

## 6. Подключаем приложение

Осталось указать прокси самому приложению. Обычно это делается в настройках HTTP-библиотеки. Адрес SOCKS5-входа — `socks5://127.0.0.1:10808`.

Проверь документацию своей библиотеки: поддерживает ли она SOCKS, нужны ли дополнительные пакеты и кто разрешает DNS-имена. Написание `socks5h` из curl подходит не всем клиентам.

Для небольшой проверки на Python можно обойтись без дополнительных пакетов. Используем второй вход — HTTP — и встроенный `urllib.request`:

```python
from urllib.request import ProxyHandler, build_opener

proxy = "http://127.0.0.1:10809"
opener = build_opener(ProxyHandler({"http": proxy, "https": proxy}))

with opener.open("https://example.com", timeout=20) as response:
    print("HTTP:", response.status)
```

Через прокси пойдут запросы, сделанные этим `opener`. Другие процессы продолжат работать как раньше. Исключение — домены из `no_proxy`: `urllib` может обратиться к ним напрямую. Это поведение описано в [документации Python 3.12](https://docs.python.org/3.12/library/urllib.request.html).

В своём приложении задай прокси для HTTP-сессии, которая отправляет запросы. При остановке приложения сессию нужно закрывать. Токен API оставь в прежнем хранилище секретов. Проверь обычный запрос, затем перезапусти службу, заменив `my-app` на её настоящее имя:

```bash
sudo systemctl restart my-app
sudo journalctl -u my-app -n 50 --no-pager
```

Проверь, возобновляет ли приложение запросы после временного сбоя сети. Если задавал переменные в SSH-терминале, учти: systemd-служба не получает их автоматически.

## 7. Восстанавливаем загрузку пакетов через APT

У меня перестала нормально работать и загрузка пакетов через APT — менеджер пакетов Ubuntu. Ему тоже понадобился отдельный сетевой маршрут. Если на твоём сервере APT скачивает обновления без ошибок, этот шаг можно пропустить.

Если ошибка связана с разрешением имени, сначала [проверь DNS](#проверка-и-замена-адресов-dns). Если с доступом к зеркалу — попробуй загрузку через уже настроенное VPN-подключение. APT умеет работать через HTTP-прокси, поэтому подойдёт второй вход Xray. Начнём с файла со сведениями о пакетах Ubuntu 24.04:

```bash
curl --noproxy '' --proxy http://127.0.0.1:10809 \
  --max-time 20 -sS -o /dev/null \
  -w 'HTTP: %{http_code}, Time: %{time_total}s\n' \
  https://archive.ubuntu.com/ubuntu/dists/noble/InRelease
```

Для этого файла ожидаем `200`. Если используется другое зеркало, проверяй его адрес из настроек APT. Успех на `example.com` ничего не говорит о доступности конкретного зеркала.

Если файла с таким именем ещё нет, создаём отдельный конфиг:

```bash
sudo nano /etc/apt/apt.conf.d/90-xray-proxy
```

```text
Acquire::http::Proxy "http://127.0.0.1:10809/";
Acquire::https::Proxy "http://127.0.0.1:10809/";
```

В обоих значениях указан `http://` — так APT подключается к локальному прокси. Когда нужен HTTPS-сайт, прокси создаёт туннель CONNECT, а клиент продолжает проверять сертификат конечного сервера. Отключать проверку TLS или подписи пакетов не нужно. Подробнее — в документации APT для [HTTP](https://manpages.debian.org/bookworm/apt/apt-transport-http.1.en.html) и [HTTPS](https://manpages.debian.org/bookworm/apt/apt-transport-https.1.en.html).

Смотрим, какие настройки применились, и пробуем загрузить списки пакетов:

```bash
apt-config dump | grep -i proxy
sudo apt-get update
```

Посмотри, нет ли в конце предупреждений о недоступных индексах. Команда может завершиться, хотя часть данных скачать не удалось. Если запросы идут не туда, проверь другие конфиги APT и настройки для отдельных хостов. Когда загрузка заработает, можно установить недостающие инструменты — например, `sudo apt-get install unzip`.

APT теперь зависит от Xray. Для возврата к прямой загрузке используй [команды отключения прокси APT](#как-отключить-прокси-для-apt).

## 8. Проверяем работу после перезагрузки

Перед перезагрузкой проверь, включён ли автозапуск Xray, приложения и остальных нужных служб — ботов, обработчиков задач, CI runners. Используй их имена на своём сервере; `my-app` ниже — пример.

```bash
systemctl is-enabled app-xray my-app
systemctl is-active app-xray my-app
```

Выбери время, когда сервер можно перезагрузить. Убедись, что нет важных выполняющихся заданий и доступна аварийная консоль. Затем:

```bash
sudo reboot
```

Повторно подключаемся и проверяем:

```bash
uname -r
systemctl is-active app-xray my-app
resolvectl status
getent ahostsv4 archive.ubuntu.com
sudo ss -ltnp '( sport = :10808 or sport = :10809 )'
curl --noproxy '' --proxy socks5h://127.0.0.1:10808 \
  --max-time 15 -sS -o /dev/null \
  -w 'HTTP: %{http_code}, Time: %{time_total}s\n' \
  https://example.com
sudo apt-get update
sudo dpkg --audit
```

Пустой вывод `dpkg --audit` означает, что команда не нашла тех проблем с состоянием пакетов, которые умеет проверять. Номер ядра и время запроса запиши для своей машины — совпадать с результатом чужого VPS они не обязаны.

### Практика с контролируемым отказом

На тестовом сервере или в согласованное окно останови Xray:

```bash
sudo systemctl stop app-xray
```

Повтори запрос через локальный прокси и попробуй открыть **новую** SSH-сессию. Запрос через прокси должен перестать работать, а SSH — остаться доступным. Посмотри, как ведёт себя приложение: сообщает об ошибке, повторяет запрос или переключается на прямой доступ. Последний вариант может не подходить для твоей задачи — это тоже нужно проверить.

Верни службу и повтори штатную операцию приложения:

```bash
sudo systemctl start app-xray
```

После запуска запросы должны снова проходить. Если этого не произошло, проверь журнал и то, умеет ли приложение повторно подключаться после обрыва. В итоге у тебя должны работать три вещи: запрос приложения через прокси, загрузка APT и отдельный доступ по SSH.

Если хочешь полностью отказаться от этой схемы, сначала верни прежние настройки приложения и [APT](#как-отключить-прокси-для-apt). Перезапусти приложение, затем отключи `app-xray` командой `sudo systemctl disable --now app-xray`.

DNS возвращается отдельно, по сохранённой конфигурации и с проверкой доступа. Остановка Xray его настройки не восстанавливает. Что нужно сохранить заранее, перечислено в разделе [«Что сохранить для восстановления»](#что-сохранить-для-восстановления).

## 9. Обновляем узел из подписки при сбое

Одной настройки оказалось мало. Через некоторое время Малена снова потеряла связь с Gemini: в журнале появилось `Cannot connect to host generativelanguage.googleapis.com:443`. В моём случае понадобилось сменить удалённый узел. Сама ошибка ещё не доказывает, что дело именно в нём: сначала стоит повторить [проверку соединения](#4-проверяем-что-запрос-проходит-через-прокси).

Чтобы не менять конфиг вручную при каждом таком сбое, я добавил скрипт `/usr/local/bin/xray-sub-update.py`. Cron запускает его каждые 10 минут. Локальный адрес прокси для бота остаётся прежним — `socks5://127.0.0.1:10808`, меняется удалённое подключение в выходе `proxy`.

### Как устроено обновление

1. Скрипт делает запрос через локальный прокси. Если соединение работает, ничего не меняет.
2. При сбое скачивает свежую подписку и получает из неё список узлов.
3. Сохраняет исходный конфиг, затем по очереди подставляет настройки кандидатов, перезапускает Xray и проверяет соединение.
4. На первом рабочем варианте останавливает перебор и перезапускает бота. Если не подошёл ни один, возвращает исходный конфиг.

Это обновление **всего профиля подключения**, а не только IP-адреса: вместе с адресом нужны порт, реквизиты, транспорт и параметры TLS/REALITY. Локальные входы и правила для остальных приложений нужно сохранить.

В этой доработке подписка возвращала Base64 со ссылками на узлы. Пример [загрузки JSON ниже](#как-получить-и-проверить-json-подписки) такой ответ не разбирает — формат и нужный User-Agent зависят от сервиса. В моём скрипте использовался `v2rayN/6.0`. Ветка `hy2` тоже была предусмотрена, но на реальном сбое её работу я не проверял: считать её подтверждённым запасным вариантом пока нельзя.

:::note Это описание моей доработки
Сам скрипт здесь не опубликован. Его имя — путь к моей программе, а не команда установки или встроенная возможность Xray. Для своей реализации можно дать нейросети этот алгоритм и описание формата подписки, убрав из примеров секреты.
:::

Ссылку подписки я вынес в `/etc/xray-sub.env` с правами `600`, журнал — в `/var/log/xray-sub.log`. Ссылка хранится как секрет; целиком выводить её в журнал нельзя. В настройках обновления нужно явно указать свой конфиг и службу: в примерах этой статьи это `/home/absolute/xray/app-xray.json` и `app-xray`.

Перед включением расписания проверь ручной запуск, возврат исходного конфига **с повторным запуском Xray** и восстановление запросов бота. Новую конфигурацию сначала проверяй через `xray run -test`, как в четвёртом шаге. Нужны также тайм-ауты и защита от одновременного запуска двух копий скрипта. Перебор перезапускает общий Xray, поэтому на это время соединение могут потерять и бот, и APT.

### Почему смена узла не спасала без DNS

Обнаружилась ещё одна зависимость по кругу: Xray отправлял DNS-запросы через тот же туннель, который перестал работать. Чтобы подключиться к новому узлу, требовалось узнать его адрес, а сделать это через неработающее подключение не получалось.

Поэтому **загрузка подписки и разрешение имени нового узла должны работать независимо от восстанавливаемого туннеля**. Список DNS-серверов сам по себе этого не гарантирует: нужно проверить, куда правила отправляют запросы с тегом `dns-out`. Если они снова уходят в `proxy`, замена адресов DNS может оставить ту же проблему. Это отдельно описано в [документации DNS Xray](https://xtls.github.io/en/config/dns.html).

В своей конфигурации я также сменил `routing.domainStrategy` с `IPOnDemand` на `AsIs`. Здесь важное уточнение: `AsIs` отключает разрешение доменов **для выбора маршрута**. Где разрешается имя назначения и как находится сам VPN-узел, зависит от остальных настроек; этот параметр не означает «весь DNS теперь удалённый». Подробности — в [справочнике маршрутизации](https://xtls.github.io/en/config/routing.html).

Проверяй через прокси именно нужный сервис, затем обычное действие бота. Доступность Google или HTTP-ответ от корня API ещё не подтверждают работу Gemini и Telegram. А если перебор не нашёл рабочего узла, начинай с журнала Xray, доступности подписки и DNS — бесконечные перезапуски причину не устранят.

## Справочник

Дальше — отдельные случаи: сомнения в работе DNS, проверка готового прокси, получение профиля из подписки и возврат настроек. Возвращайся к ним по ссылкам из основных шагов.

### Какие инструменты используются

В командах нужны `curl`, `python3`, `ip`, `ss`, `systemctl` и `resolvectl`. Для дополнительных проверок — `dig` из пакета `dnsutils` и `nc` из `netcat-openbsd`. Если APT пока не работает, начни с того, что уже установлено: например, `getent` проверяет системное разрешение имён и без `dig`.

### Где эта схема работает

Мы явно подключаем приложение к прокси. Системный TUN-интерфейс при этом не создаётся, а произвольный трафик сервера не перехватывается. UDP в нашем SOCKS-входе отключён.

В контейнере адрес `127.0.0.1` обычно указывает на сам контейнер, а не на VPS. Поэтому приложение внутри него не увидит запущенный на хосте Xray по адресам из статьи. Для такого случая подключение нужно настроить отдельно.

### Проверка и замена адресов DNS

Если DNS разрешает имена без ошибок, ничего менять не нужно. Этот раздел пригодится, когда curl не может определить адрес по имени или есть сомнения, что настроенный DNS отвечает. Сначала сравним ответы и только по результатам решим, нужна ли замена адресов.

```bash
cat /etc/resolv.conf
resolvectl status
getent ahostsv4 example.com
dig @1.1.1.1 example.com +time=2 +tries=1
dig @8.8.8.8 example.com +time=2 +tries=1
```

В этих командах `dig` обращается прямо к указанному DNS-серверу, а `getent` использует настройки системы. Если первый отвечает, а второй нет, проверяем `/etc/resolv.conf`, настройки интерфейса и systemd-resolved. Сравнение сужает поиск, но ещё не указывает точную причину.

Для временной проверки можно назначить доступные DNS-серверы интерфейсу. Сначала узнаём его имя:

```bash
ip -br link
```

В исходном случае интерфейс назывался `enp3s0`. Если у тебя другое имя, замени его:

```bash
sudo resolvectl dns enp3s0 1.1.1.1 1.0.0.1
sudo resolvectl flush-caches
getent ahostsv4 example.com
```

Это временное изменение для системы с systemd-resolved. Если оно помогло, отдельно разбери [сохранение DNS после перезагрузки](#как-сохранить-настройки-dns-после-перезагрузки). Адреса публичных DNS здесь — примеры; используй резолверы, доступные и подходящие для твоей сети.

Чтобы снова использовать штатную конфигурацию интерфейса, выполни `sudo resolvectl revert enp3s0`. Команда сбросит и другие временные настройки resolved на этом интерфейсе. Если ты их задавал, сначала запиши значения.

### Запрос без обычного DNS-разрешения

Возьми актуальный IPv4-адрес нужного домена из успешного DNS-ответа и подставь вместо `ACTUAL_IPV4`:

```bash
curl -4 -v --noproxy '*' \
  --resolve 'example.com:443:ACTUAL_IPV4' \
  --connect-timeout 5 --max-time 15 \
  https://example.com
```

Адрес подключения мы задаём вручную, а имя хоста остаётся прежним — оно нужно для HTTPS и проверки сертификата. Заменять URL на IP или отключать проверку через `-k` не требуется.

Если запрос с правильным IP тоже зависает, дело не только в обычном DNS-разрешении. Бери свежий адрес из DNS-ответа: старый IP из чужого лога уже мог измениться. Параметры команды описаны в [документации curl](https://curl.se/docs/manpage.html).

### Если уже есть внешний SOCKS5-прокси

Проверяем доступность его TCP-порта:

```bash
nc -vz -w 5 PROXY_IP PROXY_PORT
```

Открытый порт ещё не означает работающий прокси. Нужен запрос через него:

```bash
curl -v --noproxy '' --max-time 20 \
  --proxy socks5h://PROXY_IP:PROXY_PORT \
  --proxy-user 'LOGIN' \
  https://example.com
```

Замени адрес, порт и логин; при таком интерактивном запуске curl запросит пароль. Не записывай пароль прямо в команду и историю shell. Если прокси не требует авторизации, убери `--proxy-user`.

С `socks5h` имя назначения разрешает SOCKS-прокси. Какой DNS-маршрут он использует дальше, зависит от его настроек. Параметр `--noproxy ''` не даёт переменной `NO_PROXY` исключить проверяемый домен.

Если TCP-соединение устанавливается, а обмен с SOCKS-прокси зависает на рукопожатии, проверяй протокол, авторизацию, сам прокси и сеть между ним и сервером.

### Как сохранить настройки DNS после перезагрузки

Этот раздел нужен, только если [диагностика DNS](#проверка-и-замена-адресов-dns) показала проблему и новые адреса уже помогли при временной проверке. Изменение системного DNS затронет весь сервер, включая приложения без прокси.

На VPS сетевую конфигурацию часто создаёт cloud-init. Поэтому правки в его `50-cloud-init.yaml` могут быть перезаписаны. Сохрани копии текущих настроек в защищённом каталоге и посмотри, как устроена сеть:

```bash
ip -br link
ip route
sudo netplan get
resolvectl status
```

Следующий пример подходит, если интерфейс уже получает адрес по DHCP (`dhcp4: true`), а сетью управляет `networkd`. При статическом адресе или другом renderer настройку нужно адаптировать. Имя интерфейса возьми из Netplan: при использовании `match`/`set-name` оно может отличаться от вывода `ip`.

Создай `/etc/netplan/99-custom-dns.yaml`, если файл ещё не существует:

```yaml
network:
  version: 2
  ethernets:
    enp3s0:
      dhcp4-overrides:
        use-dns: false
      nameservers:
        addresses:
          - 1.1.1.1
          - 1.0.0.1
```

Адрес интерфейса и маршрут остаются в основной конфигурации — этот фрагмент их не создаёт. Посмотри итог через `netplan get`: списки из нескольких YAML-файлов могут складываться.

Если одновременно включены DHCPv4 и DHCPv6, в `networkd` нужно согласовать значения overrides. DNS из IPv6 RA приходит отдельно. Здесь важна установленная версия Netplan; подробности есть в [справочнике YAML](https://netplan.readthedocs.io/en/stable/netplan-yaml/).

Применяем с подтверждением:

```bash
sudo chmod 600 /etc/netplan/99-custom-dns.yaml
sudo netplan generate
sudo netplan try --timeout 120
```

Пока первая сессия ждёт подтверждения, во второй проверь новый SSH-вход, `resolvectl status` и `getent ahostsv4 archive.ubuntu.com`. Подтверждай только рабочий результат.

Если не подтвердить изменение, `netplan try` должен его откатить. Но у этого механизма есть ограничения: после тайм-аута или отмены нужно проверить и сеть, и YAML на диске. Перед перезагрузкой убедись, что сохранена нужная конфигурация, и при необходимости восстанови её. На такой случай и нужен доступ к консоли провайдера. Подробности — в [документации netplan try](https://netplan.readthedocs.io/en/stable/netplan-try/).

Если раньше вручную задавал `FallbackDNS`, проверь и эти адреса. Например, недоступный с твоего VPS `9.9.9.9` не поможет как резервный DNS. Добавляй туда серверы, доступность которых проверена.

### Как отключить прокси для APT

APT теперь зависит от локального Xray. Для разовой попытки прямого обновления:

```bash
sudo apt-get \
  -o Acquire::http::Proxy=DIRECT \
  -o Acquire::https::Proxy=DIRECT \
  update
```

Если для отдельных хостов заданы свои прокси или включено автоопределение, проверь эти настройки тоже. Чтобы вернуться к прежней конфигурации, перенеси созданный нами файл **за пределы** `apt.conf.d`. Выбери имя, под которым ещё нет другого файла:

```bash
sudo mv -i /etc/apt/apt.conf.d/90-xray-proxy /root/90-xray-proxy.disabled
```

Вернуть настройку:

```bash
sudo mv -i /root/90-xray-proxy.disabled /etc/apt/apt.conf.d/90-xray-proxy
```

Так отключённый файл не участвует в чтении конфигурации. Не оставляй в `apt.conf.d` копию с другим допустимым именем: APT может прочитать и её. Порядок чтения описан в [apt.conf](https://manpages.debian.org/bookworm/apt/apt.conf.5.en.html).

### Как получить и проверить JSON подписки

Здесь продолжаем [подготовку рабочего профиля](#сначала-нужен-рабочий-профиль). Даже у купленной подписки нужно выяснить формат. Нам нужен совместимый с Xray конфиг — его можно получить через доступный экспорт или из документированного формата сервиса.

В моём случае подписка возвращала массив конфигураций Xray. Это не универсальный формат: другой сервер может вернуть текст, Base64, список URI или HTML со страницей ошибки.

Ссылки вида `happ://crypt4/...` и `incy://crypt1/...` предназначены для определённых клиентов. Xray сам по себе может их не понимать. Для защищённого формата понадобится совместимый экспорт или документированный инструмент его владельца. Не отправляй ссылку случайному онлайн-декодеру и не отключай антивирус ради неизвестного конвертера.

Если собираешься использовать Python-инструмент из исходников, сначала выясни, где его настоящий репозиторий, кто автор, какая лицензия и какие версии формата он поддерживает. Проект может существовать без пакета в PyPI, но похожее имя на GitHub ещё не доказывает, что ты нашёл нужный. Не устанавливай неизвестный пакет на рабочий сервер ради одной попытки.

Когда получишь HTTPS-адрес доверенным способом, сохрани его в `subscription.txt`. Для этого создадим защищённую папку вне Git; файлы будут принадлежать текущему пользователю:

```bash
umask 077
mkdir -p ~/private-xray
chmod 700 ~/private-xray
cd ~/private-xray
nano subscription.txt
chmod 600 subscription.txt
```

Следующий скрипт рассчитан на JSON-массив. Он скачивает ответ, проверяет его основную структуру и сохраняет файл, из которого можно выбрать профиль. `User-Agent: Happ` взят из моего случая; для другого сервера используй заголовок из его документации. Не запускай скрипт с чужой или недоверенной ссылкой.

```python
import json
import os
import urllib.error
import urllib.request
from pathlib import Path
from urllib.parse import urlsplit

os.umask(0o077)
url = Path("subscription.txt").read_text(encoding="utf-8").strip()
parts = urlsplit(url)
if parts.scheme != "https" or not parts.hostname:
    raise SystemExit("Нужен HTTPS-адрес подписки")

request = urllib.request.Request(url, headers={"User-Agent": "Happ"})
try:
    with urllib.request.urlopen(request, timeout=20) as response:
        payload = response.read(5 * 1024 * 1024 + 1)
except (urllib.error.URLError, TimeoutError):
    raise SystemExit("Не удалось получить подписку; проверь соединение") from None

if len(payload) > 5 * 1024 * 1024:
    raise SystemExit("Ответ превышает лимит примера в 5 МиБ")
try:
    configs = json.loads(payload)
except (json.JSONDecodeError, UnicodeDecodeError):
    raise SystemExit("Ответ не является корректным JSON") from None

if not isinstance(configs, list) or not configs:
    raise SystemExit("Ожидался непустой массив конфигураций")
for config in configs:
    if not isinstance(config, dict):
        raise SystemExit("Элемент массива должен быть объектом")
    for key in ("inbounds", "outbounds"):
        items = config.get(key, [])
        if not isinstance(items, list) or not all(
            isinstance(item, dict) for item in items
        ):
            raise SystemExit("Некорректная структура входов или выходов")

with Path("configs.json").open("x", encoding="utf-8") as output:
    json.dump(configs, output, ensure_ascii=False, indent=2)

print("Количество конфигураций:", len(configs))
for index, config in enumerate(configs, 1):
    print("Профиль", index)
    for key in ("inbounds", "outbounds"):
        protocols = [item.get("protocol") for item in config.get(key, [])]
        print(key, protocols)
```

Режим `open("x")` защищает существующий файл от перезаписи. Перед повторной загрузкой сохрани прошлый результат под другим именем, сохранив защиту доступа. Скрипт не выводит URL, UUID и полный конфиг, но перед публикацией его вывода всё равно проверь содержимое.

Название профиля обычно находится в `remarks`. Открой файл локально, посмотри название и параметры, затем скопируй выбранный **объект** целиком в `app-xray.json`. Весь массив туда переносить не нужно. Проверяй профиль по содержимому: номер может измениться при обновлении подписки.

Если подписка недоступна с VPS, скачай её на доверенной машине и перенеси выбранный конфиг по SSH. Получение профиля не должно зависеть от прокси, который ещё предстоит настроить.

В примере HTTPS-запрос делает стандартный [urllib.request](https://docs.python.org/3.12/library/urllib.request.html). Скрипт умеет загружать конкретный формат; универсальным импортёром подписок он не является. С готовым профилем возвращайся к [установке Xray](#скачиваем-и-распаковываем-xray) или, если он уже установлен, к [настройке локальных входов](#3-настраиваем-входы-для-приложения-и-apt).

### Что сохранить для восстановления

Для восстановления понадобятся рабочий JSON, unit-файл службы, конфиг APT, сетевые настройки до и после изменений, версия Xray и имя скачанного релизного архива. Сохрани их в защищённом месте вне публичного репозитория. Проверь, что копии будут доступны, даже если сам VPS перестанет отвечать.

В доработанной схеме регулярную проверку и смену узла выполняет [скрипт по расписанию cron](#9-обновляем-узел-из-подписки-при-сбое). Дополнительно можно настроить уведомления после нескольких сбоев подряд: один неудачный запрос ещё не повод для тревоги. Для уведомлений лучше использовать независимый канал, иначе при сбое они тоже не дойдут. Такой отправки уведомлений в описанной доработке пока нет.
