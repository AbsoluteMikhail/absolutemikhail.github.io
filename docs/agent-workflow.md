# Работа агентов над gamepunk.ru

Это руководство для координатора, исполнителя и проверяющего. Начальная точка —
[AGENTS.md](../AGENTS.md): ограничения контента, архитектуры, проверок и публикации
действуют и при работе через трекеры. История чата для выполнения задачи не требуется.

## Как читать и поддерживать Wiki

1. Через `llm_wiki_projects` проверить имя и UUID проекта. Во всех последующих
   вызовах передавать `project_id` явно, не использовать `current`. Если MCP
   закреплён за другим проектом, выбрать нужный через `llm_wiki_set_project`.
2. Прочитать `wiki/index.md` через `llm_wiki_read_file`, затем найти релевантные
   страницы через `llm_wiki_search` с небольшим `top_k` (например, `5`). Не читать
   всю базу и не искать в соседних личных проектах.
3. Для архитектуры использовать `wiki/synthesis/gamepunk-architecture.md`, для
   портфолио — `wiki/synthesis/portfolio-and-mentoring.md`, для явно порученной
   работы над Академией — `wiki/synthesis/absolute-mikhail-academy.md`.
   Карта исходников — `wiki/sources/efremov-2026-gamepunk-repository.md`.
4. Прочитать первичные файлы, на которые ссылается найденная запись. Проверить
   даты `updated` и `verified`: даже свежая запись не заменяет текущий код.
   При расхождении зафиксировать его, опираться на поручение и актуальные
   проектные правила; не исправлять код под устаревшее резюме Wiki.
5. После принятого изменения обновлять только затронутые устойчивые знания:
   что изменилось, почему, канонические пути, `updated` и фактическую дату
   проверки `verified`. Не переносить туда полный отчёт, логи или список задач.
   Сначала прочитать локальные инструкции Wiki; если доступа на запись нет,
   передать координатору точное предложение правки и указать, что оно не записано.

Ответ `llm_wiki_chat` — подсказка с источниками, а не самостоятельное доказательство.
Без Wiki можно работать по исходникам, если недостающий контекст не блокирует задачу.
Запрет на `AbsoluteAcademySource/` действует также при поиске и импорте через Wiki:
обычная задача сайта не разрешает читать сырые материалы Академии.

## От запроса до подзадач

Координатор превращает обычное описание пользователя в наблюдаемый результат.
Не требовать от владельца технических формулировок, если их можно вывести из
контекста. Уточнять только существенную продуктовую развилку.

Сначала проверить существующую задачу Vikunja по ID или поиску. Идею, которая ещё
не готова к реализации, оставить в Vikunja. Для готовой работы создать небольшие
сквозные Beads: один исполнитель, один проверяемый результат. Не дробить работу
механически по файлам или на отдельные задачи «код» и «тесты».

В Vikunja записать:

```text
Результат: что пользователь сможет увидеть или сделать.
Границы: что меняем и что не входит в задачу.
Источники: пути и относящиеся к задаче решения.
Ручная приёмка: конкретный сценарий проверки владельцем.
Технический граф: ID созданных gp-* и краткое состояние, без копии всех подзадач.
```

Каждый bead должен содержать:

```text
external-ref: фактический ID GP-…; в описании — точный URL задачи Vikunja.
description: результат, разрешённый объём и исключения.
context: AGENTS.md, docs/agent-workflow.md, конкретные исходники и страницы Wiki.
acceptance: наблюдаемые критерии и необходимые команды/сценарии проверки.
dependencies: реальные блокирующие gp-*; без циклов.
assignment: исполнитель, отдельный рабочий каталог, base SHA, разрешённые файлы.
```

Приоритеты и сроки не придумывать; технический default трекера не выдавать за
решение владельца. Проверить читаемость созданных записей и связей. Повторный
запуск постановки должен продолжать существующие задачи, а не создавать дубли.

## Beads на этой машине

Из корня репозитория, в PowerShell:

```powershell
$controlScripts = 'U:\ABSOLUTE\CONTROL\scripts'
& "$controlScripts\beads_RUN.ps1" -Project gamepunk -ReadOnly -BeadsArguments @('stats', '--json')
& "$controlScripts\beads_RUN.ps1" -Project gamepunk -ReadOnly -BeadsArguments @('ready', '--json')
& "$controlScripts\beads_RUN.ps1" -Project gamepunk -ReadOnly -BeadsArguments @('list', '--json')
# Подставить существующий ID вместо gp-xxxx:
& "$controlScripts\beads_RUN.ps1" -Project gamepunk -ReadOnly -BeadsArguments @('show', 'gp-xxxx', '--json')
```

Перед мутацией проверить справку установленной версии, например `@('create',
'--help')`, `@('update', '--help')` или `@('dep', '--help')`. Wrapper поддерживает
`-ReadOnly`; для записей координатор явно убирает этот флаг и задаёт `--actor`.
Текущая версия поддерживает `create --external-ref`, `--context`, `--acceptance`
и `--body-file`. Многострочные описания передавать файлом UTF-8, не собирать
shell-команду из необработанного текста задачи.

Embedded Dolt обслуживает один пишущий процесс. Только один координатор меняет
граф; исполнители запрашивают назначение и передают отчёты ему. Даже чтение
согласовывать по очереди при конфликте блокировки. Не удалять lock-файлы и не
запускать повторный `init`. База уже инициализирована с префиксом `gp`.
В ограниченной среде даже `-ReadOnly` может потребовать разрешение на доступ к
служебным файлам Dolt вне репозитория. Использовать штатный запрос доступа;
не обходить ограничение копированием базы или удалением блокировок.

`ready` — выборка доступной работы, `awaiting-review` — метка, а не новый статус.
Координатор назначает задачу до запуска исполнителя и переводит её в `in_progress`.
После сдачи добавляет `awaiting-review`, оставляя задачу незакрытой. При блокере
записывает причину и статус `blocked`. Зависимые задачи не запускать только потому,
что исполнитель сообщил «готово»: нужна приёмка результата зависимости.

## Исполнение и передача между агентами

Перед запуском координатор проверяет отсутствие конкурирующего исполнителя и
пересечения областей изменений. Для независимых агентов использовать отдельные
worktree/checkout и ветки `codex/…`; создание таких рабочих каталогов входит в
порученный запуск работы. Общий рабочий каталог допустим только при
последовательном исполнении. Субагенты одной сессии могут разделять filesystem —
не считать их автоматически изолированными.

Worktree не переносит незакоммиченные изменения. До запуска убедиться, что там
есть актуальные инструкции и все зависимости задачи. Не коммитить пользовательские
правки ради переноса; при необходимости передать согласованный патч. Не давать
разным агентам одновременно изменять общий lockfile, общие стили или маршруты.

Стартовое поручение исполнителю:

```text
Выполни bead <gp-ID>, родитель <GP-ID и URL>.
Рабочий каталог: <абсолютный путь>; база: <SHA>.
Прочитай AGENTS.md, docs/agent-workflow.md, задачу и указанные первичные источники.
Результат и acceptance: <полный текст или доступная запись Beads>.
Разрешённые файлы/границы: <список>; зависимости: <принятые gp-ID>.
Wiki: проект e945f929-de83-46f5-a8f5-60fb9a83a0a2, страницы <пути>.
Не расширяй объём самостоятельно. При блокере верни причину и что требуется.
Сдай diff и отчёт по шаблону. Статусы записывает координатор.
Коммит, push и публикация — только если отдельно поручены.
```

Исполнитель читает `git status`, сохраняет чужие изменения, выполняет задачу и
проверки из `AGENTS.md`. Отчёт возвращает координатору через доступный канал
агентов или текущую задачу; отправка сообщений посторонним не входит в этот процесс.

```text
Задача: gp-… / GP-…
Исполнитель и рабочий каталог:
Base SHA; итоговый SHA (только если коммит разрешён) или путь к патчу:
Что изменено; список файлов:
Критерий → наблюдаемое доказательство:
Проверки: команда, результат, существенные ограничения:
Для UI: URL, размеры экрана, проверенные действия, пути к скриншотам:
Не проверено / блокеры / остаточные риски:
Wiki: что обновлено либо точное предложение обновления:
Готово к технической приёмке: да/нет.
```

Доказательства должны оставаться доступными проверяющему. Путь из чужой машины
не считать доступным артефактом; передать файл или согласованный доступ. Большие
логи и изображения хранить вне отслеживаемых исходников в выделенном локальном
каталоге доказательств; в Beads — безопасные ссылки и краткий результат.

## Независимая приёмка

«Проверь gp-…» не меняет трекер. «Прими gp-…» разрешает записать результат:

- `PASS`: все критерии подтверждены; убрать `awaiting-review`, закрыть bead с
  причиной и ссылками на доказательства.
- `REJECT`: указать конкретный дефект и повторную проверку; убрать
  `awaiting-review`, вернуть исполнителю, не закрывать.
- `BLOCKED`: указать отсутствующий доступ, решение или доказательство; не
  выдавать частичную проверку за успех.

Проверяющий читает критерии, исходники и точный diff, самостоятельно запускает
нужные проверки. Отчёт исполнителя сам по себе не доказывает выполнение. При
неразделимом пересечении с чужими правками приёмку остановить и назвать файлы.

Проверить также совместимость результатов нескольких агентов. Если интеграция
меняет уже проверенный diff, повторить затронутые проверки на объединённом
результате. Перенос изменений и коммиты выполнять в пределах поручения владельца.
Для изменения сайта сборка не заменяет браузер, а закрытый bead не означает деплой.

Когда весь технический граф принят, координатор передаёт владельцу краткий итог
и сценарий ручной проверки в Vikunja. Задачу `GP-…` закрывает владелец либо
координатор по его прямой команде. Публикация требует отдельного поручения.

## Недоступные инструменты

Vikunja запускается существующим `CONTROL/scripts/vikunja_START.ps1 -NoBrowser`,
статус — `vikunja_STATUS.ps1`. При необходимости входа использовать обычную сессию
владельца; не читать внутреннюю SQLite-базу или секреты для обхода авторизации.

Если записи недоступны, подготовить точные поля задачи или отчёта и явно отметить
«не записано». Недоступность Wiki не разрешает искать в других личных базах.
Недоступность Beads не разрешает отправлять задачи в базы других проектов.
